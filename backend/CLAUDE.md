# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

httpfly is a CLI HTTP client that runs `.http` files (REST Client / IntelliJ HTTP file syntax): plain-text request definitions with `###`-separated blocks, `# @key value` metadata, `{{var}}` variable interpolation, environments, proxying, and Lua pre-/post-request scripting. See `doc/` for user-facing docs (that's where feature detail belongs — keep this file about codebase orientation, not a duplicate of it).

## Commands

```sh
make build   # go build -o bin/httpfly ./cmd/httpfly (version injected via ldflags from VERSION)
make test    # go test ./...
make fmt     # gofmt -l -w .
make vet     # go vet ./...
make lint    # golangci-lint run (see .golangci.yml; must be installed separately)
make check   # fmt + vet + test -- run this before considering work done
```

Single test: `go test ./internal/parser/ -run TestAnalyzeResolvesFileScopedVariables -v`

Try the CLI against real requests without hitting the network:

```sh
make httpbin-up                                          # starts a local httpbin container on :8080
go run ./cmd/httpfly run doc/examples/1_basic.http
go run ./cmd/httpfly run -name Login doc/examples/3_scripting.http
go run ./cmd/httpfly validate doc/examples/invalid.http   # -name X also works here
make httpbin-down
```

`internal/client`'s tests use `httptest.Server` and don't need httpbin; `doc/examples/*.http` files are meant to be run against it manually or read as parser fixtures (`parser_test.go` reads `1_basic.http` directly). `doc/examples/3_scripting.http` works run either as a whole (`Login` and `AuthenticatedRequest` in one `httpfly run`) or as two separate invocations (`-name Login` then `-name AuthenticatedRequest`) — both exercise the login → token → authenticated-request pattern, since per-request resolution (see below) makes both cases work the same way.

## Architecture

Pipeline: `parser.ParseWithEnv` (text → structurally-validated `httpfile.File`, each `Request` carrying both a parse-time-resolved snapshot *and* its still-templated `Raw*` fields) → per request, `script.RunPreScript` → `parser.Resolve` (re-interpolate against *current* variables) → `client.Send` → `script.RunPostScript`, wired together by `internal/cli`.

- **`internal/httpfile`** — plain domain types (`File`, `Request`, `Header`). `Request` carries both resolved fields (`URL`, `Headers`, `Body`, `Proxy` — interpolated against whatever variables were visible when last resolved) and their still-templated counterparts (`RawURL`, `RawHeaders`, `RawBody`, `RawProxy`) plus `Variables` (this request's own local `key = value` declarations) — the raw fields + `Variables` are what let a request be *re-resolved* later against fresher variables (see `parser.Resolve` below). Also carries `Proxy`(-building metadata) `Lang`, `PreScript`, `PostScript`. No behavior; every other package depends on it.
- **`internal/parser`** — turns `.http` text into `httpfile.File`.
  - `parser.go`: splits the file on `###` lines into blocks (the segment *before* the first `###`, or the whole file if there's no `###` at all, is still block 0 — the *prelude*, which carries no request but may declare global variables/metadata). `Parse`/`Analyze` are thin wrappers over `ParseWithEnv`/`AnalyzeWithEnv(r, envVars)` — the latter exist so callers (the CLI) can merge in environment/persisted-state variables without changing the zero-arg entry points every existing test uses.
  - `validate.go`: structural per-block parsing (`validateBlock` and friends) — request line, headers, metadata, scripts, local variable declarations — producing a `Result` of `BlockResult{Request, Issues}` plus file-level `GlobalIssues`, a *lenient* pass that collects every `Issue` (`SeverityWarning`/`SeverityError`) instead of stopping at the first problem. Structural parsing never inspects variable values (see `Resolve` below); `Parse()`/`ParseWithEnv()` aggregate all `SeverityError` issues into one returned `error`.
  - `resolve.go`'s logic actually lives at the bottom of `validate.go`: **`Resolve(req httpfile.Request, vars map[string]string) (httpfile.Request, []Issue)`** is the other half of the pipeline — it interpolates a request's `Raw*` fields against `vars`, returning a resolved copy plus resolution issues (undefined-variable warnings, a URL/proxy that still isn't absolute once resolved). `validateBlock` calls it once, with the variables known at parse time, to populate `Analyze`'s/`validate`'s reported `Request.URL` etc. The CLI's `run` command calls it *again*, per request, immediately before sending — with whatever variables are current *at that point* (which may include a value an earlier request's post-request script just set) — see `internal/cli/run.go`. This is what makes scripting-set variables available both to a later block in the *same* `httpfly run` and to a later, separate invocation; there used to be a restriction that only the latter worked (interpolation was parse-time-only), removed once real usage surfaced the gap.
  - `@name` is **mandatory** on every request block and **local-only** (an error if declared in the prelude) — it's the sole identifier used for `-name` scoping in the CLI (`internal/cli/select.go`).
  - Metadata scope: `localOnlyMetadata`/`knownMetadataKeys` in `validate.go` control which `@key`s are prelude-eligible (`proxy`) vs. request-only (`name`, `lang`). Unknown keys are warnings regardless of scope.
  - Variable precedence, highest to lowest: request-local `key = value` > persisted `client.global` (as current as of whenever resolution actually runs) > `-env` environment > file-global (prelude). `mergeVars` composes these; `globalVars := mergeVars(preludeVars, envVars)` then `vars := mergeVars(globalVars, localVars)` per block/resolution.
  - `< {% ... %}` / `> {% ... %}` script blocks are captured (not executed) here — `scriptBlock`/`extractPostScript`/`isScriptOpenLine`. `checkScriptSyntax` compiles (via `gopher-lua`'s `LoadString`, never runs) a script during validation, so syntax errors surface without any of a script's side effects.
  - A resolved header still gets kept even if interpolation left an unresolved placeholder in it — only a genuinely malformed header *line* drops the header (see `hasError` in `validate.go`; this was a real bug once, don't reintroduce it).
  - `IsUndefinedVariableIssue(issue Issue) bool` is exported specifically so `internal/cli` can escalate an undefined-variable *warning* (fine at parse/validate time — a script might still set it) into a hard error at actual send time (no more "might" left by then).
- **`internal/interpolate`** — `Apply` (raw substitution: headers, body) and `ApplyURL` (query-parameter *values* get percent-encoded; the host/scheme prefix and path segments are substituted raw, so a `{{host}}` variable holding a full `scheme://host` prefix isn't mangled). Source-agnostic: doesn't know or care where `vars` came from.
- **`internal/client`** — `Client.Send(ctx, httpfile.Request) Result` over `net/http`. A non-nil `Result.Err` means the request couldn't be sent/read (transport failure); a 4xx/5xx response is a normal `Result` with `Err == nil`. Also captures `FinalURL` (after redirects) and `TLS` (`*tls.ConnectionState`, nil for plain HTTP). Routes through `Request.Proxy` when set, caching one `*http.Client` per distinct proxy URL.
- **`internal/env`** — loads a named environment (`shared` merged as defaults, then the named environment's own values) from `httpfly.env.json`, found alongside the target `.http` file.
- **`internal/state`** — persists `client.global` script variables to `.httpfly/state.json` (also alongside the `.http` file), keyed by environment name so `-env dev`/`-env prod` never share values. `Save` does read-modify-write so saving one environment's bucket never clobbers another's. A missing file/bucket is normal (empty map, not an error) — nothing's been persisted yet.
- **`internal/script`** — runs a request's Lua scripts via `gopher-lua`, preloading `cmd`/`ioutil`/`filepath`/`json` from `github.com/vadv/gopher-lua-libs` (scripts `require(...)` them by name, standard Lua module convention — `Preload` alone does *not* inject a global, a mistake made once while building this). Custom object model: `client.global:get/set` (backed by `GlobalState`, write-through to `internal/state` on every `:set`) available to both scripts; `response.status`/`headers`/`body` post-request only. No sandboxing — scripts run with full process trust, by design (see below).
- **`internal/cli`** — argument parsing and command wiring (stdlib `flag`, no Cobra).
  - `run.go`: resolves `-env` + persisted state once up front (used as the *base* variables for `parser.ParseWithEnv`, which still does one parse-time resolution pass — this is what `Analyze`/`validate` also see). Per request, `sendWithScripts` runs the pre-request script (if any, which may mutate persisted state via `client.global:set`), then calls `parser.Resolve(req, vars)` again with `vars := mergeVars(mergeVars(baseVars, global.Vars()), req.Variables)` — i.e. re-resolved against whatever's currently in `client.global`, not the parse-time snapshot — before sending, then runs the post-request script. `issuesAsSendError` elevates an `IsUndefinedVariableIssue`/`SeverityError` from that re-resolution into a hard failure (skips sending, counts toward `run`'s exit code) rather than silently sending a request with a literal unresolved `{{name}}` in it — this was a real bug caught by a user running `doc/examples/3_scripting.http` as a single whole-file invocation, before per-request re-resolution existed. Results print via `printResult`/`printJSONResults` depending on `-json`/`-s`/plain mode.
  - `validate.go`: same env+state merge as `run.go` (both feed `parser.AnalyzeWithEnv`'s one-time resolution, since `validate` never runs scripts and so never has "fresher" variables to re-resolve against), optionally narrows via `filterResult`.
  - `json.go`: `-json` output shape. `requestOutcome{Result, ScriptErr}` (defined in `run.go`) is the unit both plain-text and JSON printing consume — a post-request script error is tracked *separately* from `Result.Err` because, unlike a transport failure, the response was received fine and should still be shown/included, just flagged (`script_error` field, coexists with `response`, unlike `error` which is mutually exclusive with it).
  - `select.go`: `selectRequests` — shared `-name` lookup logic.
  - `env.go`: `resolveEnvVars` (httpfly.env.json lookup) and `mergeVars` (shared by `run.go`/`validate.go` to layer persisted state over environment vars, both at parse time and, in `run.go`, again per request at send time).

## Design decisions worth knowing before changing things

- **Host header**: deliberately *not* supported. A relative-URL-plus-`Host`-header convenience was built, tested end-to-end against httpbin, and then reverted at the user's request — `.http` files must specify a fully absolute URL. Don't reintroduce this without being asked.
- **Per-request resolution, not parse-time-only**: an earlier version of this feature resolved every `{{var}}` once, upfront, at parse time — so a script's `client.global:set(...)` could only ever affect a *later, separate* `run`, never a later request in the same one. That was a deliberate initial scope decision, but a user running `doc/examples/3_scripting.http` as one whole-file `run` hit it immediately: `AuthenticatedRequest` silently sent a literal `Bearer {{auth_token}}` instead of the real token `Login` had just fetched. Fixed by having `httpfile.Request` carry both a parse-time-resolved snapshot *and* raw (`Raw*`) templates + local `Variables`, and having the CLI's `run` command call `parser.Resolve` again per request, right before sending, against whatever `client.global` currently holds. `validate` intentionally keeps the old parse-time-only behavior (it never runs scripts, so there's nothing "fresher" to resolve against). Don't reintroduce parse-time-only resolution for `run` without a strong reason — it silently produces wrong requests instead of failing loudly.
- **No script sandboxing**: file reads and `cmd.exec` run with the full trust of the `httpfly` process. Deliberate — you write your own `.http` files, same trust model as a shell script you'd write yourself. Don't add sandboxing without being asked.
- **gopher-lua-libs dependency footprint**: importing any of its subpackages pulls a large, non-pruned (`go 1.16`) module graph into `go.sum` (AWS SDK, MySQL/Postgres/SQLite drivers, Prometheus client, ~165 lines of checksums) — verified empirically that none of it reaches actual compilation (`cmd`/`ioutil`/`filepath`/`json` only import `gopher-lua` and one small internal helper package; `CGO_ENABLED=0 go build` succeeds). This is `go.sum` noise, not a real dependency cost. Don't panic and try to replace it if `go.sum` looks alarming — it's already been investigated.
- **doc/examples/ numbering**: `1_basic.http`, `2_variables.http`, `3_scripting.http` are a deliberate walkthrough sequence (each file's header comment points to the next). `doc/examples/invalid.http` is a separate, unnumbered fixture — one deliberately broken block per validation rule, used to exercise `validate`, not meant to be run. `doc/examples/httpfly.env.json` backs `2_variables.http`'s environment examples.
